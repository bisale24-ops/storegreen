## Fixture 1 — `fixtures/tipjar-amazon` (reproduces the real CrewSheet 1.0.0 rejection)

Small Kotlin app, flavors `amazon` and `play`, one ENTITLED SKU `tipjar_pro`. Do NOT copy CrewSheet code —
same defect pattern, new neutral app.

Seeded defects:
- no `src/amazon/assets/AppstoreAuthenticationKey.pem` → AMZ-IAP-01
- `PurchasingService` service declared but no `ResponseReceiver` → AMZ-IAP-03
- `<queries>` missing, targetSdk 36 → AMZ-IAP-04
- `buy()` returns early when `getUserData` failed → AMZ-IAP-05
- release `isMinifyEnabled = true`, proguard keeps only `com.amazon.device.iap.**` → AMZ-IAP-06
- `src/amazon/res/values/strings.xml` still has "Get the full version on our website" → AMZ-IAP-07/08

Expected result: 6 findings, verdict REJECT; after `--fix` 1 finding left (the key — tool cannot invent it,
prints the exact console path to download it). Then drop in a dummy key → green.

## Fixture 2 — `fixtures/notes-play` (Google Play deadlines)

- `targetSdk = 35` → GP-API-01
- `billing-ktx:7.1.1` → GP-BILL-01
- `QUERY_ALL_PACKAGES` → GP-PERM-01
- activity with intent-filter, no `android:exported` → GP-EXP-01
- analytics SDK present → GP-DS-01, in its narrowed form: the finding lists the dependencies that
  collect data and says to declare them, and makes **no** claim about what the Data Safety form says.
  The saved form lives in the Play Console, not in a repository, so a fixture file pretending to be
  it would be the tool lying to itself. See "Three rules that cannot honestly be decided" in
  `rules-catalog.md`.

## Fixture 0 — the real bundles, and they are the acceptance test

Four shipping Amazon bundles are already on the desktop and were measured before the event started,
so the expected output is known exactly. Run bundle mode against `~/Desktop/KHLab/numsly-amazon-v7.aab`,
`lockly-amazon-v3.aab`, `scanly-amazon-v5.aab`, `smeta-amazon-v3.aab`:

- all four contain `base/assets/AppstoreAuthenticationKey.pem`, with four different SHA-256
  fingerprints → AMZ-IAP-01 passes on all four;
- all four declare the Amazon receiver, `com.amazon.venezia` and `com.amazon.sdktestclient`
  → AMZ-IAP-03/04 report "declared, structure not verifiable from a bundle";
- fifteen 64-bit native libraries in total, of which **exactly one** fails the 16 KB rule:
  `libsqlcipher.so` in Numsly, `p_align 0x1000` on every `PT_LOAD`, next to sibling libraries
  already at `0x4000`;
- **exactly one bundle fires X-FLAVOR-01: Scanly**, with `com.android.vending.BILLING` in the
  manifest and `com/android/billingclient` in `classes.dex`. Numsly is the clean control.

Any other result means the implementation is wrong, not the bundles. This is also the strongest
thing in the demo: a dated, unfixed defect in an app that is on sale today, found in under a second,
versus a seeded fixture that proves nothing.
